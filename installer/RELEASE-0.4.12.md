# Aster VPN 0.4.12

Исправлены две ошибки восстановления соединения:

- Ранее сетевая ошибка API подписки прерывала начальное подключение после неудачной HTTPS-проверки и блокировала запуск ядер при автоматическом восстановлении. Теперь на запрос актуальных параметров отводится 8 секунд, после сетевой ошибки используется сохранённый профиль. Успешно полученное явное удаление/неоднозначность профиля по-прежнему требует выбора сервера. Отмена пользователя распространяется на весь процесс. Одна попытка автоматического восстановления ограничена 90 секундами.
- Ранее резервный сайт ожидал полного 12-секундного тайм-аута основного. Теперь через 2 секунды запускается резервная проверка, а первый успешный ответ отменяет остальные. Для основного адреса по умолчанию худший бюджет одного цикла уменьшен примерно с 24 до 14 секунд. Условие перезапуска осталось прежним: три цикла без единого HTTPS-ответа.

Параметры провайдера XHTTP/XMUX, режим packet-up и ядра сохранены. Новые изменения исправляют обнаружение и восстановление сбоев; увеличение скорости загрузки не доказано.

## Проверки 22.10.2026

- .NET: 116 проверок, все успешны. Новые сценарии: отказ/зависание API подписки, свежие REALITY-параметры, удалённый сервер, отмена, зависший основной HTTPS-сайт, отмена проигравшего запроса и бюджеты всех зависших проверок.
- Настоящие sing-box и Xray принимают генерируемые конфигурации.
- Локальный тест зависшего TLS: Xray 26.9.9 создаёт 30 физических соединений для 30 запросов, поставляемый 26.10.21 — 2. Повторно подтверждено ранее выполненное исправление ядра. Источник: https://github.com/XTLS/Xray-core/issues/6797 .
- Реальный сохранённый VLESS/XHTTP-профиль NL, без системного TUN: 16/16 параллельных HTTPS-запросов. Четыре параллельные загрузки Google CDN, суммарно 16 МБ: 12,4 Мбит/с; HTTPS под нагрузкой 116–286 мс.

Большой разброс повторов не позволяет приписать ограничение маршрутизатору клиента или доказать рост скорости. Под нагрузкой наблюдались задержки HTTPS до 5842 мс; оба ядра оставались запущенными.
